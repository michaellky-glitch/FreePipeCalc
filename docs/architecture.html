Architecture

How FreePipeCalc is built, and why it is built this way. Read this before you change anything.

Current to v0.18.3. The calculation methods themselves are in Calculation Method.

1. Purpose

A single-page application for Building Services Engineers. You draw a multi-level water network. It solves the flow distribution, the friction losses and the pump duty, then produces a calculation sheet and printable level plans.

It is not a web application. It is a folder of files. You open index.html and it runs. There is no server, no installation, no build step, no network access.

2. Constraints

Three rules shape every decision in this program. Each one removes options that look attractive.

2.1 Run from file://

This constraint has the widest effect.

A browser treats a file:// origin as opaque. Therefore these do not work when a user opens the folder by double-clicking:

  • <script type="module"> — ES modules are subject to CORS.
  • fetch() of a file in the same folder.
  • Web Workers. A worker also cannot load the engine, because importScripts and fetch are blocked in the same way.
  • Anything from a network: fonts, CDN libraries, analytics.
NOTE:

Every source file is a classic script in an IIFE. Each attaches to one global namespace, FD. The load order is fixed in index.html. There are no imports.

If you add a file, add it to index.html. If the engine tests need it, add it to the test load list as well.

An iframe is a navigation, not a fetch. This is why the documentation pages are HTML and are framed: they are the only documents that read correctly from disk.

2.2. Units

All model state and all calculation is metric: metres, m³/s, pascals, and metres of head. Imperial units are a formatting concern only. They live in src/units.js. Nothing in the solver may call it.

IMPORTANT:

Head is in metres of the working fluid. To convert head to pressure you need that fluid's density.

FD.units.headToPa() assumes water at 998 kg/m³. Use it only for display arithmetic where the fluid is not in scope. Anything that reports a result must use headToPaWith(h, rho).

An error here is silent: a glycol model reports water numbers. This has happened.

2.3 Build Steps and Dependencies

The program ships as source. What you read is what runs.

The one consequence you must remember is the cache. Each script tag in index.html carries a ?v= token, and FD.VERSION must equal it.

IMPORTANT:

Bump the token after you edit any file. This includes styles.css. If you do not, the browser serves the old file and your change appears to do nothing. A stale stylesheet looks exactly like a JavaScript fault.

If a change "did not take", check the token before you check the code.

4. Data flow

  1. You edit. The canvas or a panel changes the model.

  2. The edit is classified. There are three verbs, and picking the correct one is not optional — see below.

  3. The model is translated. network.build() turns levels, risers and devices into a flat list of nodes and links, and charges the fittings.

  4. The network is solved. The solver returns flows and heads.

  5. Higher passes run. Pump sizing, control loops and the thermal pass each need a solved network, and each can change it. Section 8 explains why the solve repeats.

  6. Results are published. One result object feeds the canvas, the property panel, the calculation sheet and every export.

4.1 Verbs

VerbMeaningEffect
changed()A change that can move a number.Saves, redraws, and schedules a solve.
arranged()A change to the DRAWING that the solver cannot see.Saves and redraws. No solve.
selectionChanged()Selecting is not an edit.Redraws the panel only.

Dragging a label, moving a note, bending a control leader and aligning to the grid are all real document changes that must be saved, and none of them can move a number. They are arranged().

IMPORTANT:

Ask which verb a gesture is before you wire it. The marquee once called changed() for a gesture that only writes the selection, so every click that missed a pipe cost a full recalculation. Selecting a tool did the same, so picking up the PROBE re-solved the model.

5. Disciplines

A file is one discipline. m.discipline is 'hydronic' (default) or 'plumbing'. You switch it on the chip beside the status chip, and the program warns you first, because the two disciplines share geometry but not device meaning.

NOTE:

In a plumbing file the network solver is never invoked on the DESIGN path.

Domestic water is sized from fixture units, which is a different question from a flow balance. Teaching the solver about fixture units would have put that at risk. Keeping them apart protects the mature code.

SIMULATE is the exception. The program builds a converted copy of the model in which every fixture is an ordinary pressure-dependent terminal, and runs the unmodified solver on the copy. The fixture-unit machinery never reaches the solver, and the simulation still gets real physics and real control loops. Actuator positions that the control loop settles on are copied back to the real model, because they are results.

The discipline also selects the tab set. Plumbing hides THERMAL and relabels the network tab.

6. Modes

ModePurpose
DESIGNSize components and pumps automatically based on flow demands.
CONTROLDraw sensors and control links to show the sequence of operations.
SIMULATETest system performance by applying pump curves, resistance values, and controller logic.
ANNOTATEAdd annotations, labels, notes and lines that do not interact with the model.
NOTE:

DESIGN and SIMULATE are separate modes. In DESIGN mode, flow is an input and component size is the output. In SIMULATE mode, size is an input and flow is the output.

Combining these modes into one process creates a control conflict, because one actuator cannot manage two controllers at the same time. For this reason, setpoint control works in SIMULATE mode only.

NOTE:

SIMULATE has 2 sub-modes:

  • STATIC: Prevents automatic recalculation during edits. Run the simulation once to review results safely without triggering long wait times. Recommended for large models.
  • DYNAMIC: Recalculates the model automatically on every edit for real-time adjustments. Recommended for small models.

7. Model

The model is saved as JSON file format (JavaScript Object Notation).

PartWhat it holds
levelsFloors, each with a name and an altitude. Everything drawn on a level is horizontal at that altitude.
nodesPoints. A node may carry a device: a source or an outflow.
pipesLinks between nodes. A pipe may be a plain pipe, a pump, a valve, equipment, a sensor or a riser.
risersVertical columns joining levels. They materialise into pipes when the network is built.
settingsMethod, fluid, display units, warning limits, IPC table overrides, and the monitor list.
IMPORTANT:

All pipes drawn on a level run horizontally at that level's elevation. Only risers change vertical height.

Sloped pipes are not supported. You cannot create a pipe with different endpoint heights on the same level.

Saved files carry a formatVersion. Loading merges the saved settings over current defaults, so new settings will be added to a file written by an older build.

8. Hydronic Network Solver

The full method is explained in Engine documentation.

8.1 Global Gradient Algorithm (GGA) Iteration

A single solve only calculates flows for fixed inputs. Because flow resistance, pump duty, and controller positions change each other's input conditions, a single solve cannot produce a complete answer. The solver must run multiple iterations until all variables stabilize.

Iterative dependencies include:

  • Flow resistance: Tee fitting loss depends on whether flow goes to the run or the branch, but flow direction is unknown until after an initial solve.
  • Pump sizing: Required pump duty depends on the pressure drop to the worst terminal, but that pressure drop changes as pump duty updates flows.
  • Controllers: A controller adjusts an actuator, which changes network pressure and flow, which in turn alters the sensor reading driving the controller.

Each iteration step performs a full network solve until the system stabilizes.

NOTE:

If a complex system does not stabilize, increase the number of iterations in Settings>Setpoint Control

8.2 Non-blocking execution

The solver runs as a generator, yielding control after each network solve:

CallerExecution method
solveModel()Executes all iterations continuously. Used for tests and exports.
Application UIExecutes iterations on a 24 ms budget using setTimeout to keep the UI responsive in all browser states.
NOTE:

If the user edits the model during an active solve, the application increments app.solveEpoch and cancels the running calculation to prevent invalid results.

8.3 Negative pressure

The DESIGN solve is demand-driven. Negative pressure indicates insufficient head to satisfy the demand.

This number represents the missing head required for pump sizing—it is not a physical pressure. Use SIMULATE mode to calculate actual delivered flow.

8.4 Open/Closed loop detection

The software detects whether a system is open or closed from the drawing geometry. Closed circuits automatically receive a reference datum node for absolute pressure calculation.

8.5 Pump sizing

Pumps set to Automatic sizing adjust duty until the worst-served terminal receives required pressure.

IMPORTANT:

SIMULATE reads every pump from a curve. A pump carries one whatever its sizing mode, so a model sized in DESIGN is ready to simulate without a mode change.

  • AUTO / MANUAL: the program generates a curve from the pump's design point (its flow and head), shaped by the shutoff and runout percentages in SETTINGS.
  • CURVE: the pump uses pasted manufacturer data.

8.6 Thermal calculation

The thermal module solves temperature using a single linear system after hydraulic calculations complete. Temperature does not feed back into hydraulic calculations.

Junction temperatures use flow-weighted averages. Pipe heat loss calculations use pipe insulation and external surface coefficients.

NOTE:

Fluid density changes due to temperature variations are not simulated.

9. Domestic water

The full method is explained in Engine documentation.

FunctionRole
M.plumbingSizingTraces the network from the source to accumulate downstream fixture units and generic flow.
network.plumbingReportApplies pipe friction and calculates forward residual pressure for DESIGN mode.
network.plumbingSimModelConverts plumbing fixtures into pressure-dependent terminals for SIMULATE mode.
network.plumbingPumpDutyCalculates booster pump duty in a single linear pass based on residual pressure.
IMPORTANT:

Always use the appropriate discipline for your system type. Plumbing fixtures use IPC table values rather than standard hydronic demand fields. Accessing raw hydronic properties (such as flow or reqPressure) on a plumbing fixture returns invalid data.

NOTE:

To avoid calculation and sizing errors, always use the M.plumbing* helper functions when working with domestic water networks.

10. Fittings

Fittings are automatically generated from the piping arrangement.

Because tee leg assignments (run vs. branch) depend on flow direction, fitting loss calculations are updated after an initial solve, requiring a second solve iteration (see Section 8.1).

11. Canvas and panels

11.1 The canvas

canvas.js owns rendering, hit testing and every gesture. It draws the active level solid and a neighbouring level faded, so you can see what you are connecting to.

NOTE:

An invalid fillStyle or strokeStyle does not raise an error. The canvas keeps the last colour it was given.

So a missing theme key does not look like a colour fault. It looks like whatever was drawn immediately before. Text boxes were once painted in the background colour on top of a background-coloured panel: created correctly, drawn correctly, invisible.

When a colour looks wrong, check that the value is a string.

11.2 Property panel levels

LevelDescription
L1 — IdentityBasic item identification (always visible).
L2 — SectionsCollapsible categories (Design, Actual, Control, Display) that retain open/closed states.
L3 — TooltipsExplanatory notes accessed through the 🛈 icon.
IMPORTANT:

The property panel rebuilds on every solve. To prevent edits from being written to the wrong element mid-render, input handlers use commit() guards to reject inputs from outdated panel states.

12. Warnings and errors

The full list of error messages is documented in MESSAGES documentation.

All message detection is performed by the engine and shared across the entire application.

Message severity levels:

  • Error: Calculation is invalid or impossible. Cannot be dismissed.
  • Defect: Geometry or logic conflict in the drawing. Cannot be dismissed.
  • Warning: Results are valid, but exceed typical engineering thresholds.
  • Notice: Informational message to clarify specific calculated values.
IMPORTANT:

Numerical convergence does not guarantee a valid drawing. The engine separately checks geometry for breaks, disconnected islands, unjoined coincident nodes, and unsupported configurations.

14. Testing

The suite contains over 2,200 assertions across 10 test files, running on native Node.js with no external dependencies. Run all tests with:

for f in test/*.test.js; do node $f; done
IMPORTANT:

Test expectations must come from independent hand calculations, never copied directly from engine outputs. Document the reason before updating any expected test baseline.

  • Fixtures: Tests read frozen fixture files in test/fixtures/. Files in examples/ and debug/ are not used by tests and can be excluded from production builds.
  • Generators: Scripts named test/testrun-*.js regenerate files in examples/; they are not test suites.
  • Harness: test/harness.js loads data and engine layers. Test suites append the specific modules they exercise.
IMPORTANT:

Custom test harnesses must load thermal.js when testing control logic. Omitting it causes runControlsGen to exit early, making control loops fail silently.

Deployment is handled by GitHub Actions. The test workflow gates production deployment—if tests fail, the build will not publish.

16. Limitations

See Known Issues section in README.

17. Changes

  1. Bump the ?v= token and FD.VERSION together. Including for a stylesheet change.
  2. Never invent engineering data. If a number cannot be sourced, ship it flagged or do not ship it. A synthesised fitting column was once 250% wrong against the real table. An invented correction is not defensible to a checking engineer.
  3. Add the message code to the catalogue. The test checks both directions.
  4. Choose the right verb — changed, arranged or selectionChanged.
  5. Report a result with headToPaWith, never the bare headToPa.
  6. Reconstruct a loss with linkLoss(link, q). Reading link.r alone omits the fitting term. The number still looks like a pressure drop. It is just too small.
  7. Do not replace a span of code you have not read. Replacing the text between two names deleted fifty-three functions once, and ten another time, because the two names were not adjacent. Match the exact text.
  8. Release state on every path. A latch that only clears on success is a fault waiting for its first exception.
  9. Do not mirror input state you can read directly. A key-up that lands in another window never arrives, so a tracked modifier stays stuck after you switch application.
  10. Verify on a server, not from file://. Bind it to the loopback address.
